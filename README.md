
## **🔹 설계 의도 (Design Decisions)**

  

### **1. Entity와 DTO를 분리한 이유**

  

본 프로젝트는 외부에 공개되는 API 형태의 서비스이기 때문에

DB 구조를 그대로 노출하는 것을 피하고자 응답 전용 DTO를 사용했다.

이를 통해 엔티티 구조 변경이 API 스펙에 직접적인 영향을 주지 않도록 설계했다.

---

### **2. 랜덤 조회 시 ID만 먼저 조회한 이유**

  

랜덤으로 하나의 문자를 선택하는 데 전체 컬럼 정보는 필요하지 않다고 판단했다.

따라서 먼저 조건에 맞는 ID 목록만 조회한 뒤,

선택된 ID에 대해서만 단건 조회를 수행하여 불필요한 데이터 로딩을 줄였다.

---

### **3. 비즈니스 예외를 Service 계층에서 처리한 이유**

  

해당 타입의 문자가 존재하지 않는 경우는 단순한 기술 오류가 아니라

도메인 규칙에 따른 예외 상황이라고 판단했다.

이에 따라 비즈니스 로직을 담당하는 Service 계층에서 예외를 발생시키고,

Controller에서는 이를 HTTP 응답으로 변환하는 역할만 담당하도록 분리했다.

---

### **4. 전역 예외 처리(GlobalExceptionHandler)를 사용한 이유**

  

Controller마다 예외 처리를 반복하는 것을 방지하고,

API 응답 형식을 일관되게 유지하기 위해 전역 예외 처리를 적용했다.

이를 통해 클라이언트는 항상 동일한 구조의 에러 응답을 받을 수 있다.
